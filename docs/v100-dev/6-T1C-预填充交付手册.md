```
1) Q f32→half 转置 + K/V q8_0 反量化      （t1c_*_kernel）
1.5) 设备符号接线 + V 三段 guard（center/amax/power-of-two 缩放）  ← 必须在 PV 之前

4) store：vacc/psum*scale+center → llama [d,h,t] 布局
```

## 4. 已定罪并修复的缺陷（**别再重走**）

| # | 症状 | 根因 | 定位方法 | 修法 |
|---|---|---|---|---|
| 1 | 非法访存 + 之后所有 `cudaMemcpy` 读回全 0 | PV epilogue 解引用**空设备指针**：`g_row_sum_out`/`g_row_max` 从未接线 | `[T1C] ERR s2b-sync: illegal memory access` + 全 0 dump | 每次调用 `cudaMemcpyToSymbolAsync` 接线（**宿主源用每设备 pinned 槽**，勿用栈变量） |
| 2 | 256K 必炸（潜伏越界） | `kt` 按 `kHeadDim*kRows` 申请（6.3 MB），实际需 `kHeadDim*kv_len`（256K ⇒ 134 MB） | 静态算尺寸 | 按 `kMaxTotalKV` 申请 |
| 3 | ≥2 个前缀块时算错 | K 是 **dim-major** `[d][kv]`，块偏移应为 `+begin`（元素）而非 `+begin*256` | 对照 1cat 参考实现 `key_transposed + begin` | 改指针偏移 |
| 4 | PV 权重用未缩放 V | V 三段 guard 排在 PV **之后** | 对照参考实现顺序 | guard 移到第一次 PV 之前 |
| 5 | 服务跑一层后"假死" | 每调用把 `rows(12288)` 个 float 的 state **回写调用方的 24-float 栈数组** = 爆栈 | 崩溃点 + ABI 尺寸 | 删掉该回写（llama 侧不需要） |
| 6 | `psum` 放大 **12.9x**、输出被摊平 | PV **融合行和的行映射错位**（反解 eff_shift 命中**别行**的 pmax：row5→row2620、row6→row4） | 宿主参考对拍 + `REFSHIFT` 探针 | 自建 `t1c_row_sum_kernel` 覆盖（**后被 #7 取代**，现默认关） |
| 7 | **每 tile 后 64 行**分子错（maxdiff 2.9/33/3.6） | `PREFIX_PV_M128_W64_ROW_SUM` 的自动开启挂在 `PREFIX_TORCH_EXTENSION` 下，我方 OBJECT 构建未定义 ⇒ A-transform 的 `row_max` 只有 8 槽（单访问），而 M128/W64 线程图每线程有 **2 个 contiguous 访问**（行 0..63 / 64..127）⇒ 后 64 行套用前 64 行 max | **行级指纹**：row0/16/60（local<64）对、row100/127（local≥64）错、row128/129（下一 tile local<64）又对 + `REFCAND` 探针否掉"整行搬家/相加" | **把该宏补进宏圣经**（顺带让 PV 自带融合行和恢复正确 ⇒ 撤掉 #6 的核，**收回 16.1 s**） |
| 8 | 引擎自身 276.8 s（vs 融合核 168 s）| **自伤**：入口每调用末尾无条件 `cudaStreamSynchronize` ⇒ 4 个 head-group 调用（分居 4 卡）全串行，每调用白等 13-14 ms | 分 prefix 拟合 `t ≈ 14.4 ms + 0.2064 µs×prefix`（边际已 61 TFLOPS ⇒ 问题在固定项） | 热路径**零同步**（只留 `cudaGetLastError`）；同步一律 `if (t1c_verbose)` ⇒ 276.8 → 25.9 s |

**诊断方法学（值得复用）**：数值二分最优顺序 = **score → num → psum → out**，逐层用**宿主复算**对齐；"行级指纹"比整体误差更能指认线程图类 bug。

## 5. 剩余可选优化项（按性价比排序，含方向与预期）

> 全部为**可选加固**：当前已"打平 BL1"，下列任一项 ≥3 s 的收益即可把"打平"变成"稳健反超"。

### 5.1 KV 反量化每调用全量重算（**首选**，预期 3-8 s）
- **现象**：每次调用对**整个 kv** 做 K/V 的 q8_0→half 反量化（O(kv)），而一个 chunk 内 64 个调用里，**同一层的 K/V 只有该 chunk 新增的 2048 token 是新的**。
- **方向**：per-device 增量缓存：记 `(k_ptr, kv_len)`，只反量化新增段；或把 K 直接以 q8_0 喂给 QK（1cat 有 `PREFIX_QK_Q8_DIRECT` 之类的直读路线，见 `LLAMA_SM70_Q8_DIRECT`）。
- **验证**：`T1C_DUMP=1` 看 `s1b kv-deq` 耗时占比；256K 末端 chunk 该值最大。
- **风险**：低（数值可比对门值）。

### 5.2 `kBlockN` 调档（预期 2-5 s + 省 400 MB/卡）
- 现值 `PREFIX_TORCH_BLOCK_N=24576` ⇒ scores 工作区 `rows×kBlockN×2B` = **604 MB/卡**。
- 降到 **8192** ⇒ 200 MB/卡，且 K 维更短、L2 命中更好；代价 = 前缀循环块数 ×3（每块一次 cuBLAS+PV 启动开销）。
- **做法**：改宏圣经里 `PREFIX_TORCH_BLOCK_N`，逐档测（8192 / 12288 / 16384）。**注意**：`kMaxTotalKV` 与 workspace 计算式一起核。

### 5.3 前缀 K 的 dim-major 反量化写非合并（预期 1-3 s）
- `t1c_k_q8_0_to_half_t` 写 `kt[dd*kv_len + tok]`（步长 = kv_len ⇒ 非合并写）。
- **方向**：改成 tiled 转置（32×32 共享内存 tile，参考文件里已有的 `transpose_half_32x32`）；或让 QK 直接吃 token-major（改 `key_stride`/布局，风险高）。

### 5.4 tail 与下一块前缀的双流重叠（1cat 原设计未启用，预期 1-3 s）
- 参考实现有 `concurrent_tail_scores` 双流编排；我方 tail 是串行追加。
- **做法**：为 tail 起独立 stream + event 依赖，与下一调用/下一块的前缀 QK 重叠。

### 5.5 修正后 PV 的 M128/W64 归约开销（**净收益不明，需先测**）
- #7 的宏补丁让 PV 走"跨 8 warp 归约"拓扑（每 tile 一次 smem 归约）。若其开销 >0.5 s，可试 `PREFIX_PV_SKIP_ROW_SUM` + 自建**廉价**行和核（**注意**：上一版自建核每次多读 2.9 GB ⇒ 代价 16.1 s，**别重犯**；要做就做 tiled/向量化的版本）。

### 5.6 显存换时间/时间换显存
- scores 604 MB + `kt`(134) + `vhalf`/`vscaled`(2×134) ≈ 1.00 GB/卡。若要**更少卡**（3 卡达标 = 优）或更大 ctx，5.2 的调档 + KV 直读（省 f16 镜像）是两条现成路径。

### 5.7 通用化（工程性，非性能）
- 当前准入：`q ≤ 2048`、`q % 8 == 0`、`kv % 32 == 0`、`hq/hkv == 6`（per-group）。
- 若换模型（不同 GQA 比 / head_dim），需同步：`kRows = q*heads_q`、`kHeadDim`、`t1c_tail_tri_mask` 的 `/heads_q`、`kBlockN` 预算。

## 6. 工装陷阱清单（每条都真实踩过）

1. **CRLF 上传即静默失败**：pwsh `Set-Content` 写 CRLF ⇒ `bash script.sh` 首行重定向带 `\r` ⇒ **秒退、无日志**。上传后一律 `sed -i 's/\r$//' <file>`。
2. **MCP 单次调用 15 min 上限**：长链（构建+起服+压测）会被掐断，且**可能连带 tmux server 消失**。拆成"起活"与"结束符阻塞等待"两段；等待用 `while ! grep -q MARKER log; do sleep 30; done`。
3. **不要从脚本里 `tmux kill-session -t <自己所在的会话名>`** —— 脚本会自杀（表现为"会话立刻没了"）。驱动脚本用独立会话名，服务用 `srv`。
4. **`pkill` 括号式自保**：命令里同时出现"括号式模式"和"裸名"会自匹配杀自己。杀/启分令。
5. **宿主解引用设备指针 = 段错误**：`ws.psum[row]`（设备地址）在宿主读 ⇒ 进程直接消失。必须先 `cudaMemcpy`。
6. **扫描/计数读回必须有序**：`cudaMemsetAsync + kernel + cudaMemcpy` 在非阻塞流上会读到旧值 ⇒ 出现 `bad > n` 的**假计数**。用 `cudaMemcpyAsync(...,stream)+cudaStreamSynchronize`。
7. **`cudaMemcpyToSymbolAsync` 的宿主源不能是栈变量**（删同步后会悬垂）⇒ 用每设备 `cudaMallocHost` 槽位。
8. **复制而非合并**：`Copy-Item -Recurse` 合并目录会留 untracked 污染，`git checkout` 清不掉（要 `git clean`）。
9. **CMake 源属性对本 TU 无效**：必须 `#define` 直写源 + 平铺 + `target_include_directories` 三件套。
10. **正式环境红线**：`/root/llm/llama.cpp`、`/root/llm/systemd` **只读**（本文档流程已改用自建启动器 `/root/libdir-gb/llama-server`）；正式服务卡位 `CUDA_VISIBLE_DEVICES=2,5`，测试用 `0,1,2,3` ⇒ **GPU2 有重叠风险**，跑前确认正式服务未运行。

## 8. 已试过但**未采纳**的路线（灰名单，勿重复投入）

| 路线 | 结果 | 原因 |
|---|---|---|
| 切 `PREFIX_PV_WARP_SPECIALIZED` | 未做 | 该路径 `static_assert(PVOutputElement == Element)`，与我们的 **FP32 分子**输出冲突；且 FP16 分子有溢出风险（实测 75310 > 65504，见 P3RSK） |
| 用 cuBLAS 做 PV（`P̃` 物化） | 否 | 物化流量 ≈ 1.2 GB/块（256K）⇒ 比省下的算力更贵 |
| 自建行和核覆盖 PV 融合和 | **已关**（`T1C_OWSUM`） | #7 修好后 PV 自带行和已正确；自建核每调用多读 2.9 GB ⇒ **-16.1 s** |
| q8-direct KV 直读（省 f16 镜像） | 灰（显存使能件） | 实测预填充 **-3.6%**（窄块读 > 反量化转换成本），见 R318 |
