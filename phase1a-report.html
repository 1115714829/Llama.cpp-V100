1. What was ported

Upstream PR #27858 makes draft-dflash work when the lm_head is split along the vocabulary. Its core idea: when --split-mode tensor is active, skip the in-graph selector and rank the candidates on the host, reading the selector tables straight from the draft GGUF. The port covers exactly the 7 files of that diff, plus the removal of a temporary diagnostic I had added to ggml/src/ggml-backend-meta.cpp.

Conclusion 1 — the port is correct

The very same host-selector code path, same draft, same tensor split now yields mean accepted length 4.31–6.22 — the level of the official Q4_K_M number (5.39), and of the earlier single-card official-condition run (4.92). A buggy port could not suddenly become good just by changing the target. The "port has a bug" hypothesis is excluded.

Conclusion 2 — the ~4% is target incompatibility

Q2_K_XL target → mean len 4.3–6.2. TurboFCFusion Q4_K_M target → mean len 1.2–1.4. Same draft, same code. The DFlash2 draft consumes the target's extracted layer input embeddings (n_extract=5) and the target's lm_head; it was trained on the base Qwen3.8-27B, while TurboFCFusion is a merged/fine-tuned variant with its own MTP head and output head. The candidate ranking collapses.
⇒ DFlash2 cannot be used with the production TurboFCFusion model short of retraining the draft.

Conclusion 3 — even on a compatible target, DFlash2 is slower than MTP

Higher mean accepted length (4.3–6.2 vs 3.4–4.2) but lower throughput (46.8 / 50.9 / 67.2 vs 66.3 / 68.5 / 81.1 t/s): DFlash2 must read a separate 1.14 GB draft model every step. On a bandwidth-bound decode that costs more than the extra acceptance buys. This matches the earlier three-prose-prompt result (37.88 vs 40.66 t/s).

5. Correction to the earlier record

An earlier note in dflash-in-llamacpp.md §10.2 claimed dflash 66.7 > mtp 40.66 t/s. Those two arms used different prompts (reasoning type vs prose type) and were therefore not comparable. This run's same-prompt comparison shows MTP ahead by ~31%. The claim is retracted; on V100, MTP is the faster speculative scheme.

6. What this means for the project goal

"Reach 1cat-vLLM's speed (DFlash2 + FP8, 120–200 t/s)" does not hold on this box, for three independent reasons:

  • the production target is incompatible with the DFlash2 draft (§4);
  • on a compatible target DFlash2 is still slower than MTP — bandwidth-bound (§4);
  • V100 has no FP8 (SM_89/SM_90 only) — the 120–200 t/s figure rests on different hardware premises.

Practical output of the speculative-decoding line: freeze and document the MTP configuration (--spec-type draft-mtp --spec-draft-n-max 4) and show, with data, that DFlash2 is not the answer here. Phase 1a's engineering value is fixing an open upstream crash and proving the host-side selector correct — not a speedup.
